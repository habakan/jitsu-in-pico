# 位置づけ

何を作っていて、誰のどんな問題を解くのか。公開と資金申請（OpenSats など）の前提になる文書。
技術的な中身は [architecture.md](architecture.md)、判断の経緯は [design.md](design.md)。

## 一文で

**取引の中身を読み解く部分を鍵から切り離し、同じバイナリをデバイスでもブラウザでも動かせるようにした
エアギャップ署名器。** 署名するときに画面へ出る内容を、誰でも自分の手元で再現して確かめられる。

## 誰のどんな問題か

ハードウェアウォレットは、攻撃者が中身を決められるデータ（PSBT、QR、UR）を必ず解析する。
ここが最大の攻撃面でありながら、**どの実装も自前で書いていて、利用者が中身を確かめる手段がない**。

- 利用者から見ると「画面に出ている送金先と金額が本当に正しいか」を、デバイスを信じる以外に確かめられない
- 開発者から見ると、解析器の不具合が鍵に届く。解析と署名が同じメモリ空間にいる実装がほとんど
- 第三者から見ると、出荷されたファームの中の解析器が、公開ソースと同じものかを確かめにくい

## 主張の軸: 同じコードがどこでも動く。ただし鍵は動かさない

コンセプトを図で説明したものは [everywhere.md](everywhere.md)。

「どこでも動く」のは**鍵を持たない部分だけ**にする。ここを混ぜると安全性の説明が崩れる。

| | デバイス（RP2350） | PWA / ブラウザ | 検査環境（PC・QEMU） |
|---|---|---|---|
| `parser.wasm`（PSBT・UR の解析、表示モデルの素） | 動く | 動く | 動く |
| 鍵・BIP32 導出・署名 | **ここだけ** | 動かさない | テスト用の鍵のみ |
| カメラ・液晶 | 実機 | カメラ API / 画面 | なし |

この分け方から出てくる性質:

1. **デバイスが見せる内容を、手元で再現できる。** 同じ PSBT を PWA に食わせれば、デバイスの画面と同じ
   解析結果が出る。食い違えばどちらかがおかしい
2. **成果物のハッシュを突き合わせられる。** デバイスは自分が積んでいる `parser.wasm` の SHA-256 を画面に出す。
   PWA 側で同じ値を確認できれば、「手元で動かしているものと、デバイスの中身が同じ」と言える
3. **解析器だけを独立に検証できる。** 15.6KB の WASM 1 個。ファジングも再現可能ビルドも現実的な大きさ
3.5. **別々のランタイムで突き合わせられる。** デバイスは WAMR、ブラウザは V8 / JavaScriptCore / SpiderMonkey で
   同じバイト列を動かす。結果が食い違えば、どちらかのランタイムがおかしいと分かる。
   実際に見つけた [WAMR の非整列 `i64.store`](https://github.com/wasm-micro-runtime/wasm-micro-runtime/pull/5123) は
   まさにこの種類の問題だった（QEMU では再現せず、実機でだけ落ちた）
4. **オフラインで渡せる。** PWA は一度開けば機内モードでも動く。単一 HTML に `.wasm` を埋めて
   USB メモリで渡すこともできる。アプリストアも通信も要らない

## PWA に鍵と署名も載せるか

載せる。ただし**用途を 3 つに分け、既定は鍵なし**にする。混ぜると「鍵はデバイスだけ」という
運用上の線引きが曖昧になり、ブラウザにシードを入れる習慣を作ってしまう。

| モード | 鍵 | 使う wasm | 用途 |
|---|---|---|---|
| **相方（既定）** | 持たない | `parser.wasm` | PSBT の表示、UR の受け渡し、デバイスの解析器ハッシュ照合 |
| **検証** | 公開のテスト鍵のみ | `parser.wasm` + `bitcoin-signer.wasm` | 同じ入力からデバイスと同じ署名が出るかを手元で再現する |
| **回復** | 本物のシード | 同上 | デバイスが壊れたときの最後の手段。オフライン必須、警告を出す |

載せる理由:

- **「同じコードがどこでも動く」が完成する。** 解析だけでなく署名まで同じバイナリになるので、
  デバイスの出力をブラウザでビット単位に再現できる。これは言葉ではなく実行で示せる検証手段になる
- **材料が既にある。** `bitcoin-signer.wasm` は 34,410 byte で import 0 個。
  Mac ネイティブ / Mac WAMR / RV32 ネイティブ / RV32 WAMR の 4 経路で、BIP340・BIP39・BIP84 の
  ベクタが一致することを確認済み（[feasibility.md](feasibility.md)、[kdf-feasibility.md](kdf-feasibility.md)）
- **回復手段になる。** デバイスが壊れた・無くした場合に、オフラインのページだけで署名できる道が残る。
  ハードウェアに依存しきらない設計は、それ自体が利用者の利益になる
- **ハードが無くても検証できる。** 第三者が署名ロジックを確かめるのに、基板を買う必要がない

### 配る手段とプラットフォームの制約

Service Worker の登録には HTTPS（または localhost）が要るので、**「PWA をオフラインで注入する」は厳密にはできない**。
代替手段は OS で事情が違う。

| | Android | iOS |
|---|---|---|
| 単一 HTML をファイルで渡す（wasm を base64 で埋める） | **できる**（USB / SD / Bluetooth でコピーし `file://` で開く。SW 不要） | **できない**（Safari はローカル FS を開けず、Files のプレビューでは JS が制限される） |
| 一度オンラインで読み、ホーム画面に追加してから機内モード | できる（WebAPK） | できる（iOS 16.4 以降は Chrome / Edge / Firefox の共有メニューからも）。ただしオフラインの制約が多い |

この制約はモードの分け方と噛み合う。

| モード | 推奨する環境 | 理由 |
|---|---|---|
| 相方（鍵なし） | スマホでよい | 鍵が無いので、入手経路が多少弱くてもリスクが小さい |
| 検証 | どこでも | 公開のテスト鍵しか使わない |
| **回復（本物のシード）** | **デスクトップで、ハッシュを検証した単一 HTML をオフラインで開く** | スマホにシードを入れるのは、入手経路を検証できない以上避ける |

守る条件:

- **既定モードでは鍵の入力欄を出さない。** 検証・回復モードは明示的に切り替えたときだけ
- **読み込み後は通信しない。** 単一 HTML に `.wasm` を埋めてオフラインで配れる形にし、ハッシュを公開する。
  `file://` でも動くよう `WebAssembly.instantiate(arrayBuffer)` を使う（`instantiateStreaming` は MIME 型を要求する）
- **シードを保存しない。** `signer_zeroize` を呼び、localStorage にも IndexedDB にも書かない
- **PBKDF2 を WebCrypto に差し替えない。** 速くはなるが、デバイスと違うバイナリになり「同じコード」の主張が崩れる
- 「シードを入力させる web ページ」は偽物を作られやすい形式でもある。配布方法とハッシュの公開を手順として固める

## 構成要素

| | 役割 | 状態 |
|---|---|---|
| [wasm-psbt-parser](https://github.com/habakan/wasm-psbt-parser) | PSBT と UR の解析、Plan 生成、署名の差し込み、UR 符号化。import 0 個、15,598 byte | 動作。非公開 |
| wasm-bitcoin-signer（本リポジトリの `signer/` を切り出す） | BIP39 シード、BIP32 導出、ECDSA / Schnorr 署名。import 0 個、34,410 byte | 動作。未分離 |
| 署名器（本リポジトリ） | 参照実装。RP2350 + カメラ + 液晶。**常用で鍵を置くのはここだけ** | signet で一巡。非公開 |
| PWA（相方） | 上の 2 つの wasm を載せる。既定は鍵なし、検証と回復のモードを別に持つ | 未着手 |

**2 つの wasm が部品、デバイスが参照実装、PWA が検証と回復の相方**、という形で見る。
デバイス側は解析器だけを wasm で動かし（[architecture-b.md](architecture-b.md) の案 B）、
署名はネイティブで行う。PWA 側は両方を wasm で動かす。**同じソースから出た同じバイナリ**を、
置かれた環境に応じて使い分ける。

## 既存との違い

| | SeedSigner | Krux | Jade | 本設計 |
|---|---|---|---|---|
| 解析と鍵の分離 | 同一プロセス | 同一 VM | 同一ファーム | **WASM サンドボックス** |
| 解析器を単体で検証 | - | - | - | **同じ `.wasm` を PC・ブラウザで実行** |
| OS | Linux | なし（MicroPython） | なし | なし |
| CPU | BCM2835（非公開、VideoCore が先に起動） | K210（RTL 非公開） | ESP32 | **Hazard3（RTL 公開）** |
| RAM | 512MB | 8MB | 520KB | **520KB（実使用 341KB）** |
| 成熟度 | 実運用多数 | 実運用中 | 製品 | signet で一巡 |

CPU の RTL が公開されている点は補助的な性質として添える。主題にはしない
（Krux も RISC-V であり、RP2350 の boot ROM は非公開なので「完全にオープン」とは言えない）。

## 安全性の説明が崩れない理由

「どこでも動く」と聞くと鍵が広がるように見えるが、そうならない設計にしてある。

- `parser.wasm` は **import を 1 個も持たない**。時計もメモリ確保もネットワークも触れない
- 受け渡しは固定長 5,016 byte の `plan_t` 1 枚。ホストは線形メモリの範囲を検証してからコピーする
- **ネイティブ側が Plan を再検証する。** 解析器が嘘をついても、鍵の導出と所有確認は独立に行う
- 画面に出した内容と署名対象が一致することは、`core_sign` が `core_review` 済みの Plan の
  SHA-256 一致を要求することで担保する
- PWA は鍵を扱わない。ウォッチオンリーの表示と UR の受け渡しに限る

## 公開前に積む準備

公開してからでは直しにくいものを先に片づける。

1. **再現可能ビルド。** 第三者が同じ `parser.wasm`（同じ SHA-256）を出せること。
   clang / wasi-libc の版を固定し、手順を文書化する
2. **継続ファジング。** 解析器への libFuzzer を常設し、コーパスを公開する。OSS-Fuzz も視野
3. **仕様書。** `plan_t` のレイアウト、ホスト ABI、受理する PSBT の範囲と拒否する条件
4. **xpub 出力。** これが無いと PC 側にも鍵が要り、エアギャップの主張が成立しない
5. **デバイスでの解析器ハッシュ表示。** 上の主張 2 の土台
6. **英語化。** 解析器は既に英語。本体は公開時に英語で書き直す

## OpenSats の評価軸との対応

[申請の観点](https://opensats.org/apply)は Bitcoin への影響・FOSS・透明性/教育の 3 つ。

| 観点 | 当てはめ方 |
|---|---|
| Bitcoin への影響 | ハードウェアウォレット共通の攻撃面（PSBT・QR 解析）に、再利用できる隔離された実装を出す |
| FOSS | MIT。解析器・署名器・PWA すべて公開。再現可能ビルドで成果物まで検証できる |
| 透明性・教育 | 実測と失敗を全部残している（AOT の XIP が 7 倍遅い、WAMR の非整列 `i64.store` など）。
手順と計測方法も公開するので、他のプロジェクトが同じ検証をやり直せる |

既に[上流へ還元した実績](https://github.com/wasm-micro-runtime/wasm-micro-runtime/pull/5123)がある
（WAMR の非整列 `i64.store` 修正、2026-09-30 マージ）。

## 想定される反論と答え

| 反論 | 答え |
|---|---|
| WASM ランタイムの分 TCB が増えるのでは | 増える。ただし増えるのは**鍵に触れない側**で、減るのは**攻撃者の入力を触る側**。実測で WAMR は Flash 約 100KB、プール 160KB |
| 遅いのでは | PSBT 解析 25ms。一巡の 3% しか占めない。AOT にしても 8% しか変わらないのでインタプリタのままでよい |
| 他プロジェクトは WASM を飲まない | 飲まなくてよい。(1) 同じ C ソースを直接リンク (2) AOT でネイティブ化 (3) サンドボックスが要る所だけ WASM、の 3 形態で出す |
| 機能が足りない | 足りない。単署名の P2WPKH / P2TR だけ。マルチシグ・パスフレーズ・xpub 出力は未実装 |
| ブラウザは信用できない | 鍵を置かないので、ブラウザが壊れても鍵は漏れない。表示の食い違いはデバイスの画面が正とする |
