# 位置づけ

何を作っていて、誰のどんな問題を解くのか。公開と資金申請（OpenSats など）の前提になる文書。
コンセプトの図は [everywhere.md](everywhere.md)、技術的な中身は [architecture.md](architecture.md)、
判断の経緯は [design.md](design.md)。

## 一文で

**署名器の中身を、UI から切り離した部品にした。** 取引を読み解く部分と鍵を扱う部分を
それぞれ import を持たない WASM にしてあるので、どんな言語・どんな画面の裏にでも置ける。
**実機（RP2350）も単一 HTML のビューアも、その部品を使う用例の 1 つ**という関係になる。

## 誰のどんな問題か

ハードウェアウォレットは、攻撃者が中身を決められるデータ（PSBT、QR、UR）を必ず解析する。
ここが最大の攻撃面でありながら、**どの実装も自前で書いていて、利用者が中身を確かめる手段がない**。

- 利用者から見ると「画面に出ている送金先と金額が本当に正しいか」を、デバイスを信じる以外に確かめられない
- 開発者から見ると、解析器の不具合が鍵に届く。解析と署名が同じメモリ空間にいる実装がほとんど
- **署名器を作りたい人から見ると、毎回ゼロから書くことになる。** PSBT・UR・BIP32・署名を
  自前で実装し、自前でテストする。そこが各実装でばらばらなまま重複している

## 部品

| | 大きさ | import | 役割 |
|---|---:|---:|---|
| [wasm-psbt-parser](https://github.com/habakan/wasm-psbt-parser) | 15,598 B | 0 | UR の復元、PSBT の解析、表示モデル（`plan_t`）の生成、署名の差し込み、UR 符号化 |
| wasm-bitcoin-signer（本リポジトリの `signer/` を切り出す） | 34,410 B | 0 | BIP39 シード、BIP32 導出、ECDSA / Schnorr 署名 |

どちらも **import を 1 個も持たない**。時計もメモリ確保もネットワークも触れない。
受け渡しは固定長 5,016 byte の `plan_t` 1 枚なので、ホスト側の境界が単純になる。

### どの言語からでも呼べる

| ホスト | 動かし方 |
|---|---|
| C / 組み込み | WAMR（実機で使っているもの） |
| ブラウザ | そのまま |
| Dart / Flutter | WAMR を FFI、または wasmtime |
| Kotlin / Android | Chicory（純 Java のランタイム、JNI 不要）または WAMR + JNI |
| Swift / iOS | WasmKit（純 Swift）または WAMR を C 相互運用で |
| Rust | wasmtime / wasmi |
| Go / Java | WasmEdge（C / Rust / Go / Java / Python の SDK がある） |
| Python / CI | wasmtime-py、Node |
| サーバ・エッジ | WasmEdge。ウォッチオンリーの裏側や CI での検証に |

言語内で完結するランタイムがあるので、ネイティブのビルド環境を持ち込まずに済む。

**どのランタイムを使うかは、こちらが決めることではない。** import を 1 個も持たず WASI も使わないので、
「WASM を実行できる何か」であれば何でもよい。上の表は例であって、指定ではない。
MCU では WAMR のように組み込み向けのものが要る（WasmEdge は OS を前提にしていてベアメタルでは動かない）。

## 用例（どれも参照実装）

### 1. ベアメタルの署名器（本リポジトリ）

RP2350 + カメラ + 液晶。OS なし、RAM 520KB。解析器だけを WASM で動かし、署名はネイティブで行う
（[architecture-b.md](architecture-b.md) の案 B）。**常用で鍵を置くのはここだけ。**
signet で一巡し、PC に鍵を置かない運用まで確認済み（[signet.md](signet.md)）。

### 2. 単一 HTML のビューア（`make viewer`）

189KB の HTML 1 枚に 3 つの WASM を埋めてある。オフラインで配れて、PSBT の中身を手元で確かめられる。
Android の `file://` でも動くことを実機で確認した。**鍵は扱わない。**

### 3. これから作るもの

同じ部品の上に、好きな UI を載せられる。モバイルのネイティブアプリ、デスクトップのツール、
別のハードウェア。**部品は変えずに、殻だけ差し替わる。**

## 主張の軸: 同じコードがどこでも動く。ただし鍵は動かさない

「どこでも動く」のは**鍵を持たない部分だけ**にする。ここを混ぜると安全性の説明が崩れる。

| | デバイス（RP2350） | ビューア / PWA | 検査環境（PC・QEMU） |
|---|---|---|---|
| `parser.wasm` | **同じバイト列** | **同じバイト列** | **同じバイト列** |
| 鍵・BIP32 導出・署名 | **ここだけ** | 動かさない（回復モードを除く） | テスト用の鍵のみ |
| カメラ・液晶 | 実機 | カメラ API / 画面 | なし |

この分け方から出てくる性質:

1. **デバイスが見せる内容を、手元で再現できる。** 同じ PSBT をビューアに食わせれば同じ解析結果が出る。
   食い違えばどちらかがおかしい
2. **成果物のハッシュを突き合わせられる。** デバイスは `Parser hash` で自分が積んでいる
   `parser.wasm` の SHA-256 を表示する。ビューアも同じ値を出し、`make check-repro` で手元から
   同じハッシュを再現できる（[reproducible-build.md](reproducible-build.md)）。**3 点が揃う**
3. **解析器だけを独立に検証できる。** 15.6KB の WASM 1 個。ファジングも再現可能ビルドも現実的な大きさ
4. **別々のランタイムで突き合わせられる。** WAMR / V8 / JavaScriptCore / SpiderMonkey で同じバイト列を動かす。
   結果が食い違えばランタイムがおかしい。実際に見つけた
   [WAMR の非整列 `i64.store`](https://github.com/wasm-micro-runtime/wasm-micro-runtime/pull/5123) が
   その例（QEMU では再現せず、実機でだけ落ちた）
5. **オフラインで渡せる。** 単一 HTML に `.wasm` を埋めて USB で配れる。アプリストアも通信も要らない

## 実際に動かして確かめた環境

ベアメタル MCU（RP2350）、ブラウザ、Android 10（A80）、iOS、Linux / macOS、Node。
**OS の無いマイコンと iPhone の Safari で、同じ 15,598 byte が動く。**

## 鍵を扱う側（ビューアの将来のモード）

`bitcoin-signer.wasm` も載せられるが、**用途を 3 つに分け、既定は鍵なし**にする。
混ぜると「鍵はデバイスだけ」という運用上の線引きが曖昧になる。

| モード | 鍵 | 用途 |
|---|---|---|
| **相方（既定）** | 持たない | PSBT の表示、UR の受け渡し、解析器ハッシュの照合 |
| **検証** | 公開のテスト鍵のみ | 同じ入力からデバイスと同じ署名が出るかを手元で再現する |
| **回復** | 本物のシード | デバイスが壊れたときの最後の手段。オフライン必須、警告を出す |

守る条件: 既定モードでは鍵の入力欄を出さない。読み込み後は通信しない。シードを保存しない。
PBKDF2 を WebCrypto に差し替えない（速くなるがデバイスと違うバイナリになり「同じコード」が崩れる）。

### 配る手段とプラットフォームの制約（実測）

Service Worker の登録には HTTPS が要るので、**「PWA をオフラインで注入する」は厳密にはできない**。
単一 HTML をファイルで渡す形なら回避できるが、カメラだけは出所の規則に縛られる。

| | Android | iOS |
|---|---|---|
| 単一 HTML をファイルで渡し `file://` で開く | **できる**（2026-10-03 に A80 / Android 10 で確認） | できない（Safari はローカル FS を開けない） |
| その `file://` のページでカメラを使う | **できない**（`NotAllowedError`） | 同上 |
| 一度オンラインで読み、ホーム画面に追加 | できる | できる |
| ネイティブの殻（WebView）に入れて配る | **できる**（APK を直接渡せる。カメラも使える） | 実質できない（App Store か 7 日の開発者署名） |

カメラが使えるかは**ページの出所**で決まる。`http://192.168.x.x` のような LAN の http は
安全なコンテキストではないので、`navigator.mediaDevices` ごと存在しなくなる。

## 既存との違い

| | SeedSigner | Krux | Jade | 本設計 |
|---|---|---|---|---|
| 解析と鍵の分離 | 同一プロセス | 同一 VM | 同一ファーム | **WASM サンドボックス** |
| 解析器を単体で検証 | - | - | - | **同じ `.wasm` を PC・ブラウザで実行** |
| 他の実装から使えるか | - | - | - | **部品として配る前提** |
| OS | Linux | なし（MicroPython） | なし | なし |
| CPU | BCM2835（非公開） | K210（RTL 非公開） | ESP32 | **Hazard3（RTL 公開）** |
| RAM | 512MB | 8MB | 520KB | **520KB（実使用 341KB）** |
| 成熟度 | 実運用多数 | 実運用中 | 製品 | signet で一巡 |

CPU の RTL が公開されている点は補助的な性質として添える。主題にはしない。

## 安全性の説明が崩れない理由

- `parser.wasm` は **import を 1 個も持たない**
- 受け渡しは固定長 5,016 byte の `plan_t` 1 枚。ホストは線形メモリの範囲を検証してからコピーする
- **ネイティブ側が Plan を再検証する。** 解析器が嘘をついても、鍵の導出と所有確認は独立に行う
- 画面に出した内容と署名対象が一致することは、`core_sign` が `core_review` 済みの Plan の
  SHA-256 一致を要求することで担保する
- QR のデコーダは環境ごとに違ってよい。**デコーダは信頼の起点ではなく**、出力は必ず解析器が検証する

## 公開前に積む準備

部品として使ってもらう前提なので、**仕様書が最優先**になる。

1. **ABI の仕様書。** `plan_t` のレイアウト、入口の関数、エラーコード、受理する PSBT の範囲と拒否する条件。
   これが無いと他の言語から呼べない
2. **ホスト実装の例をもう 1 つ。** 今あるのは C と JS だけ。Dart か Kotlin か Swift のどれか 1 つあれば、
   「どの言語でも」が言葉でなく実物になる
3. **ABI の版管理。** 構造体を変えたら壊れるので、版番号と互換の約束を決める
4. **継続ファジング。** 解析器への libFuzzer を常設し、コーパスを公開する。OSS-Fuzz も視野
5. **英語化。** 解析器は既に英語。本体は公開時に英語で書き直す
6. ~~再現可能ビルド~~ 済（[reproducible-build.md](reproducible-build.md)）。`address.wasm` と
   `qr.wasm` と `bitcoin-signer.wasm` も対象に広げる
7. ~~xpub 出力~~ 済。~~デバイスでの解析器ハッシュ表示~~ 済

mainnet を使う前提としては、SWD の切り離しと第三者レビューが残っている
（[architecture-b.md](architecture-b.md) §15）。

## OpenSats の評価軸との対応

[申請の観点](https://opensats.org/apply)は Bitcoin への影響・FOSS・透明性/教育の 3 つ。

| 観点 | 当てはめ方 |
|---|---|
| Bitcoin への影響 | ハードウェアウォレット共通の攻撃面（PSBT・QR 解析）に、**他の実装が再利用できる部品**を出す。各実装が自前で書いている部分を共通化し、検証を 1 か所に集められる |
| FOSS | MIT。部品・実機・ビューアすべて公開。再現可能ビルドで成果物まで検証できる |
| 透明性・教育 | 実測と失敗を全部残している（AOT の XIP が 7 倍遅い、WAMR の非整列 `i64.store`、`wasm-opt` が PATH にあるだけで成果物が変わる、quirc が液晶の遠景を読めない）。手順も公開するので、他のプロジェクトが同じ検証をやり直せる |

既に[上流へ還元した実績](https://github.com/wasm-micro-runtime/wasm-micro-runtime/pull/5123)がある
（WAMR の非整列 `i64.store` 修正、2026-09-30 マージ）。

## 想定される反論と答え

| 反論 | 答え |
|---|---|
| WASM ランタイムの分 TCB が増えるのでは | 増える。ただし増えるのは**鍵に触れない側**で、減るのは**攻撃者の入力を触る側**。実測で WAMR は Flash 約 100KB、プール 160KB |
| 遅いのでは | PSBT 解析 25ms。一巡の 3% しか占めない。AOT にしても 8% しか変わらないのでインタプリタのままでよい |
| メモリ安全な言語なら要らないのでは | その通りで、Dart や Rust で書かれたウォレットにサンドボックスの利点は薄い。そこでの価値は**実装間の突き合わせ**と**ハードウェア機との同一性の証明**になる |
| 他プロジェクトは WASM を飲まない | 飲まなくてよい。(1) 同じ C ソースを直接リンク (2) AOT でネイティブ化 (3) サンドボックスが要る所だけ WASM、の 3 形態で出す |
| 機能が足りない | 足りない。単署名の P2WPKH / P2TR だけ。マルチシグとパスフレーズは未実装 |
| ブラウザは信用できない | 鍵を置かないので、ブラウザが壊れても鍵は漏れない。表示の食い違いはデバイスの画面が正とする |
